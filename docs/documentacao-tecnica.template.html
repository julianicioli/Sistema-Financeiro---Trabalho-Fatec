1. Arquitetura da solução

O usuário acessa um frontend estático (HTML5, Tailwind CSS e JavaScript com fetch) hospedado na Vercel. Ao executar uma simulação, o navegador orquestra três funções serverless, cada uma em um provedor de nuvem pública. A AWS é chamada primeiro (cascata) porque o montante que ela calcula alimenta as outras duas, que são chamadas ao mesmo tempo (paralelo, com Promise.allSettled). Não há máquinas virtuais nem contêineres gerenciados pelo grupo: só PaaS e FaaS.

Resiliência (graceful degradation)

  • Cada chamada tem tempo limite de 4 s (AbortController). Erro HTTP, falha de rede/CORS ou timeout ativam o fallback local só daquele módulo: o card mostra "Serviço Temporariamente Indisponível", usa a mesma fórmula da função no navegador e exibe o botão Tentar de novo, que refaz apenas a chamada que falhou.
  • Se a AWS falhar, o montante é calculado localmente e Azure e GCP continuam funcionando; Azure e GCP não dependem uma da outra.
  • Os interruptores Simular falha enviam ?simularErro=true: a própria nuvem responde HTTP 500, que aparece no console de logs do provedor durante a demonstração.
  • Um X-Request-Id comum às três chamadas aparece nas respostas e nos logs, permitindo localizar a mesma simulação em AWS, Azure e GCP.

Segurança

  • O frontend só conhece as três URLs públicas; não há chave de API, segredo ou credencial no código nem no GitHub. As APIs de câmbio são públicas e chamadas de dentro da função Azure.
  • CORS restrito ao domínio da Vercel (e localhost:5173 para desenvolvimento) na AWS e na Azure; na GCP o CORS é tratado no código.
  • As três funções validam a entrada e respondem 400 com a lista de campos inválidos.

As três funções recebem e devolvem Content-Type: application/json, aceitam POST (e OPTIONS de CORS) e respondem 200 (sucesso), 400 (parâmetros inválidos) ou 500 (falha interna, inclusive a simulada com ?simularErro=true). 2.1 AWS Lambda — Calculadora de Juros Compostos

M = P(1+i)n + A·[(1+i)n − 1]/i, com aporte mensal no fim de cada mês. Com tipoTaxa: "anual", i = (1 + a)1/12 − 1.

{ "aporteInicial": 1000,
  "aporteMensal": 200,
  "taxaJuros": 12,
  "tipoTaxa": "anual",
  "tempoMeses": 24 }
// Response 200
{ "status": "success",
  "provider": "AWS Lambda (sa-east-1)",
  "data": { "montanteBruto": 6616.52,

400: aportes negativos ou ambos zerados, taxa fora de 0–100, meses fora de 1–600, tipoTaxa diferente de mensal/anual.

3. Análise de métricas e desempenho

Metodologia. As três funções ficaram {{ESPERA}} minutos sem receber chamadas. Em seguida, um script Node.js (o mesmo fetch usado pelo navegador) fez a 1ª chamada às três ao mesmo tempo (cold start) e depois {{NWARM}} chamadas seguidas a cada uma, com 1 s de intervalo (warm start). A latência é medida no cliente, a partir de uma conexão de internet no Brasil (região de Campinas/SP), e inclui rede, TLS, plataforma e execução. Medição feita em {{DATA}}.

Leitura dos resultados

{{ANALISE}}
  • Distância de rede: a Lambda está em São Paulo, enquanto a função Azure está no Canadá e a GCP em Iowa (EUA). Parte da diferença de warm start é só o caminho de rede até cada região, não a velocidade do provedor.
  • Por que existe cold start: após um período sem tráfego as plataformas desligam as instâncias (escala para zero). A 1ª chamada precisa iniciar o ambiente Node.js e carregar o código; as seguintes reaproveitam a instância já pronta.
    • {{IMPACTO}}
  • Como reduzir: Provisioned Concurrency (AWS), instâncias "sempre prontas" do Flex Consumption (Azure) e mínimo de instâncias > 0 (Cloud Run) eliminam o cold start, mas passam a cobrar pelo tempo ocioso.

O painel "Métricas de Latência" do frontend registra cada chamada feita pelo navegador (cold/warm, HTTP, Request-Id) e exporta CSV, permitindo repetir esta medição durante a apresentação. Os dados brutos desta tabela estão em docs/metricas-latencia.json no repositório.

4. Relato técnico comparativo

Comparação feita a partir do que o grupo efetivamente configurou em cada console durante o deploy.

AspectoAWSAzureGCP
IAM / permissões É preciso criar uma role de execução (trust policy para lambda.amazonaws.com + AWSLambdaBasicExecutionRole). A Function URL pública exige duas permissões na política da função: lambda:InvokeFunctionUrl e lambda:InvokeFunction. A primeira URL do grupo respondia 403 AccessDenied justamente por falta delas. A assinatura Azure for Students tem uma política que só permite algumas regiões (Brazil South foi recusada) e cota zero para o plano de Consumo clássico (Y1). Foi preciso usar o plano Flex Consumption em Canada Central. O acesso público é definido no código (authLevel: 'anonymous'). Exige vincular faturamento ao projeto e ativar as APIs (Cloud Run Admin, Cloud Build). No 1º deploy o console pediu para conceder roles/run.builder à conta de serviço padrão. O acesso público é uma opção simples na criação ("Permitir acesso público").
CORS Configurado na própria Function URL (origens, métodos e headers). Quando o código também enviava Access-Control-Allow-Origin, a resposta saía com o header duplicado e o navegador bloqueava; a solução foi deixar o CORS só na Function URL. A plataforma intercepta o preflight OPTIONS: sem origens cadastradas ele volta 204 sem headers de CORS, mesmo com o código tratando CORS. Foi necessário cadastrar as origens no Function App (az functionapp cors add). Tratado no código da função (headers e resposta 204 ao OPTIONS); funcionou sem configuração extra na plataforma.
Logs e monitoramento CloudWatch Logs (grupo /aws/lambda/juros-compostos), com a duração faturada e o Init Duration de cada cold start; métricas no próprio console da Lambda. Application Insights criado junto com o Function App: logs, falhas, dependências (chamadas às APIs de câmbio) e live metrics. Aba Observabilidade/Registros do Cloud Run e Logs Explorer, com métricas de requisições, latência e instâncias.
Processo de deploy Rápido pelo CloudShell: zip do index.mjs, create-function, create-function-url-config e add-permission. Atualizações com update-function-code em segundos. O mais trabalhoso: o Flex Consumption não tem editor no portal; o deploy foi um zip com node_modules enviado pelo Azure Cloud Shell (az functionapp deployment source config-zip). O arquivo host.json original tinha um erro de digitação que impediria a função de iniciar. O mais simples: editor in-line no console (index.js + package.json + ponto de entrada) e "Salvar e reimplantar"; build automático em ~1 min.
Observações Região de São Paulo disponível, o que deu a menor latência de rede. A AwesomeAPI respondia 429 para os IPs compartilhados da Azure; adicionamos a ExchangeRate-API como segunda fonte antes da tabela fixa. Crédito de teste (R$ 1.830 por 90 dias) e limite de 2 instâncias configurado para evitar custo.

Facilidades e dificuldades

  • Mais fácil para começar: GCP, pelo editor in-line e pela opção direta de acesso público. Mais controle: AWS, com permissões explícitas e CORS declarativo na Function URL. Mais restrições de conta: Azure for Students (regiões e cotas), o que levou a mudar o plano de hospedagem.
  • CORS foi o ponto que mais exigiu teste nas três nuvens: cada uma trata o preflight de um jeito (Function URL, plataforma do App Service, código). Testar com curl -X OPTIONS antes de ligar o frontend evitou erros difíceis de ver no navegador.
  • Contrato único (mesmo formato de erro, simularErro e X-Request-Id) simplificou o frontend e a demonstração de resiliência.

5. FinOps — estimativa para 1 milhão de requisições por mês

Premissas: 1.000.000 de execuções por mês em cada função, duração média de 100 ms, memória configurada (AWS 256 MB, Azure 512 MB, GCP 512 MiB / 1 vCPU) e respostas de ~1 KB. Valores aproximados em dólar a partir das tabelas públicas de preço sob demanda; conferir nas calculadoras oficiais antes de usar em orçamento.
